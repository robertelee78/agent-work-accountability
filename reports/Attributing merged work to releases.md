# Record the integrated commit, then attribute releases

The skill can reliably attribute a `next` story to its first published GitHub Release. The graph question is already solved: whether a release contains a commit has an exact answer. On the two pilot repositories, a local `git tag --contains` and the API-only `compare/{tag}...{sha}` test **agreed on 128 of 128 issues** with a known commit. Each API answer cost **at most 4 compare calls** using binary search. The hard part is knowing *which commit* is the story's change. In repo-to-cve (r2c), every change since v0.1.6 arrives as a PR merge, and **6 of 8 closed managed issues have a machine-readable closing PR**. In vox, work lands as local `merge: #N` commits and direct pushes, and **0 of 2 closed issues and only 2 of 33 Done-but-open issues** have any GitHub link to a commit on `main`. So the recommendation is mainly about evidence, not algorithms. awa should add an `integration` evidence record that names the SHA GitHub put on the default branch, and bind it to the accepted candidate. It should then compute "first release" from that record using a fixed precedence and the published Release list. Every situation the owner listed (no linked change, shallow clone, backport, revert, tag without a Release, conflicting references) should produce a named `unknown` with a question, not an answer. Under that strict rule, a backfill over today's pilots gives an outright answer for **3 of 10** closed issues. It gives a proposed answer needing one confirmation for 3 more, and returns `unknown` for 4. Most of the remaining gap is in vox's older issues. New work becomes attributable once agents follow one portable convention: put a `Work-item:` trailer on the integrating commit, and record that commit as evidence.

## Containment is exact; change identity is the real problem

Both ways of testing containment give exact answers. Run locally, `git tag --contains` and `git merge-base --is-ancestor` give exact graph answers ([git-tag](https://git-scm.com/docs/git-tag)). Over the API, `GET /repos/{o}/{r}/compare/{TAG}...{SHA}` returns `behind` or `identical` exactly when the SHA is an ancestor of the tag. It returns `ahead` or `diverged` otherwise ([REST compare](https://docs.github.com/en/rest/commits/commits#compare-two-commits)). The pilot saw all four statuses. `diverged` correctly flagged second-parent ancestors, such as r2c `73fa5b6eb0`, as not yet released. GitHub has **no documented "tags containing this commit" API**. The commit page's tag list comes from the undocumented `branch_commits` web endpoint, which a portable skill must not depend on ([discussion #78161](https://github.com/orgs/community/discussions/78161)). Mature tools such as semantic-release, release-drafter and release-please all do the same thing: compute a commit range between releases, then map commits to PRs through `associatedPullRequests` ([release-drafter](https://github.com/release-drafter/release-drafter/blob/main/packages/github-adapter/src/index.ts); [release-please](https://github.com/googleapis/release-please/blob/main/src/github.ts); [semantic-release/github](https://github.com/semantic-release/github/blob/master/lib/success.js)).

Several shortcuts give the wrong release and should be ruled out in the skill's text. `git describe --contains` picks the "more direct" path, not the earliest tag. In linux.git it attributed a 2013 commit to v4.6-rc1 instead of v3.13-rc1 ([git list](https://ratatoskr.run/git/2016/06/7678232/t)). A local experiment found three more failures. Lexical tag order puts `v0.10.0` before `v0.3.0`. `--sort=version:refname` puts `-rc` after the final release unless `versionsort.suffix` is set. A lightweight tag takes its commit's date, so it can look earlier than the real release. Generated release notes are filtered by label and author, leave out direct pushes, and come from a rate-limited POST endpoint ([generated notes](https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes); [REST Releases](https://docs.github.com/en/rest/releases/releases)). Release-note text is worse. vox's v0.2.9 notes mention #40, #41, #50, #51 and #173 under "Known issues" and "Moved to v0.2.10". Naive `#N` parsing would credit all five to v0.2.9, and every one of those is wrong ([vox v0.2.9](https://github.com/robertelee78/vox/releases/tag/v0.2.9)).

The GitHub-native links to a change are uneven, and each has its own trap. `Issue.closedByPullRequestsReferences` returns only *open* PRs by default. A tool must pass `includeClosedPrs: true` to see the PR that already merged ([GraphQL schema](https://github.com/octokit/graphql-schema/blob/main/schema.graphql)). The timeline's `ClosedEvent.closer` reports what actually closed the issue: a `PullRequest`, a `Commit`, or a `ProjectV2`. It is null for a manual close. Closing keywords count only on PRs that target the default branch. A keyword in a commit message closes the issue but does not link the PR ([linking PRs](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)). The probe must be `merge_commit_sha` after merge: the merge commit, the squash commit, or the rebased tip. Before merge, that field holds a test-merge SHA that never lands. The PR's head SHA is never on `main` after a squash or rebase ([REST Pulls](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request)). This matters directly to awa. Its `candidate` evidence is the commit that was accepted. The test fixtures model it as a commit URL ([scenario.py:138](../tests/scenario.py)). That commit is often a branch commit, not the commit that reached `main`.

## The attribution rule as a decision procedure

The owner's rule becomes a short procedure. **If the story names a release, use that tag**, but still verify that the integration commit is an ancestor of the tag. If it is not, report `unknown: named tag does not contain the change`. **Otherwise the story is `next`.** Resolve its change in this order:

1. The `integration` evidence awa recorded.
2. `ClosedEvent.closer`: a merged PR's `mergeCommit`, or a `Commit`.
3. `closedByPullRequestsReferences(includeClosedPrs:true)`, filtered to merged PRs.

Timeline `ReferencedEvent` commits and `#N` subject matches are **candidates to show a person, never evidence**. Then test containment against published, non-draft Releases in `published_at` order, and stop at the first one that contains the commit. A story with several recorded integration commits is delivered by the first release that contains **all** of them. The pilot shows why. Using the *latest* change agreed with the project's own records in every case checked. Using the *earliest* would have wrongly put vox #40 and #41 in v0.2.9, when both issues record "Target moved to v0.2.10" ([vox #41](https://github.com/robertelee78/vox/issues/41); [commit 946a62a920](https://github.com/robertelee78/vox/commit/946a62a920)).

| Condition | How awa detects it | Result |
|---|---|---|
| No integration evidence, closer, or merged closing PR | All three lookups empty | `unknown: no linked change`, listing timeline candidates |
| Shallow or incomplete checkout | `git rev-parse --is-shallow-repository` is true, or tags are missing compared with `git ls-remote --tags` | Use the API path; never report "not released" from a shallow repository |
| Tag without a Release precedes the first published release | A containing tag with no Release, or only a draft, sorts before the first published one | `unknown: tag vX has no Release`, proposing the next published release |
| Backport | An integration commit is on a non-default branch, or `(cherry picked from commit …)` appears in a release-line tag | `unknown: backport`, listing each line's first release |
| Revert | A later commit before the candidate tag says "This reverts commit <sha>", or a merged PR is titled "Revert …#N" | `unknown: reverted before vX` |
| Conflicting references | The computed release differs from a version the story's own evidence names, or release order by version disagrees with `published_at` order | `unknown: conflict`, showing both |
| Mutable tag moved | The peeled tag SHA differs from the stored one | Recompute; an immutable release is final |

Four precision rules come from the sources and the local experiment. First, a shallow clone gives **silent false negatives**. With the commit present and truly an ancestor, `is-ancestor` still returned 1 and `tag --contains` printed nothing, until `git fetch --unshallow --tags` was run. Blobless and treeless partial clones answer correctly. `actions/checkout` defaults to `fetch-depth: 1` with no tags ([actions/checkout](https://github.com/actions/checkout)). Second, sort releases by `published_at`, never by `created_at`. GitHub defines `created_at` as the date of the commit, and drafts are visible only to users with push access ([REST Releases](https://docs.github.com/en/rest/releases/releases)). Third, store the peeled tag SHA and the REST `immutable` flag with each attribution. Since immutable releases became generally available in October 2025, their tags cannot be moved or deleted. Older releases stay mutable unless republished ([GitHub Changelog](https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/)). Fourth, filter tags to the version pattern. A plain version sort puts r2c's non-version tag `m13-prereg-5eb15f4c` ahead of `v0.1.6` ([r2c tags](https://github.com/IOMachines/repo-to-cve/tags)). Backports need explicit linkage because ancestry cannot see them. In a conflicting `cherry-pick -x`, `patch-id` differed between the original and the backport, so only the trailer found it. The Linux kernel requires `commit <sha> upstream.` lines for the same reason ([stable rules](https://docs.kernel.org/process/stable-kernel-rules.html)).

The API path is the portable default, and the local path is a free accelerator. Binary search over version-sorted tags averaged **3.12 compare calls in vox and 3.52 in r2c**, against about 10 for a linear scan. It is valid only when consecutive release tags form an ancestor chain. That takes N−1 calls to check once per repository, and it held in both pilots. Finding each story's change took about 0.13 batched GraphQL queries per issue. A full local clone costs zero API calls per story, and with a commit-graph `tag --contains` runs in milliseconds even on linux.git ([Microsoft DevOps](https://devblogs.microsoft.com/devops/supercharging-the-git-commit-graph/)). Under GraphQL's 5,000 points/hour, and the 1,000 points/hour for `GITHUB_TOKEN` ([rate limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api)), both paths fit easily. One avoidable cost turned up: the `gh_account.py` wrapper makes a `GET /user` identity check on every invocation, which doubles REST calls when it wraps each request.

## Accuracy on the pilots: exact where linked, silent where not

The figures below come from read-only mirrors and GET/GraphQL queries run on 2026-10-01. They split cleanly by repository. **r2c** allows merge commits only. All 91 first-parent commits since v0.1.6 are `Merge pull request #…`, and every tag is annotated and cut on `main` ([r2c repo](https://api.github.com/repos/IOMachines/repo-to-cve)). **vox** has 243 first-parent commits since v0.1.0. 116 of them are direct pushes, and only one is a GitHub PR merge (`dc667b932d`, PR #103). Its merges are local commits such as `ec5a34f merge: #182 — …`, where `#N` is an *issue* number ([vox ec5a34f](https://github.com/robertelee78/vox/commit/ec5a34f479)). Both repositories have tags without Releases: vox v0.2.2, v0.2.3, v0.2.4 and v0.2.7, and r2c v0.1.6 and v0.1.12 ([vox releases](https://github.com/robertelee78/vox/releases); [r2c releases](https://github.com/IOMachines/repo-to-cve/releases)).

Wherever a change was identified, the computed release matched the project's own records. r2c #1255 computes to v0.1.17, as its text says. #1365 computes to untagged, matching "the remote tag remains absent". The four vox issues moved to v0.2.10 all compute to untagged ([r2c #1255](https://github.com/IOMachines/repo-to-cve/issues/1255); [r2c #1365](https://github.com/IOMachines/repo-to-cve/issues/1365)). The two disagreements are informative, not errors. First, r2c #1253 was declared "Delivered — immutable v0.1.14", then corrected in v0.1.15 and v0.1.16, then reopened. Its closing merge is exactly the v0.1.16 tag commit, which is what ADR-059 now states ([r2c #1253](https://github.com/IOMachines/repo-to-cve/issues/1253); [ADR-059](https://github.com/IOMachines/repo-to-cve/blob/main/docs/adr/ADR-059-private-binary-distribution-installed-lifecycle.md)). Second, #1364 was closed by a PR that only *recorded* the v0.1.14 delivery, so the closing change is a document, not the delivered code. Both failures come from treating "the issue's closer" as "the story's change". Both disappear when awa records the integration commit of the *accepted candidate*. The work model already keeps earlier delivery evidence in history when a regression reopens an item ([work-model.md:54](../skills/github-work-accountability/references/work-model.md)), so each reopen cycle gets its own attribution.

Open issues show the size of the evidence gap. Of the 41 managed issues whose Work phase is Done but which are still open, **35 have no GitHub-linked change**: 31 of 33 in vox and 4 of 8 in r2c. Most vox story IDs never appear in commit messages. V28-02 through V28-05, and nine V29 IDs, each have zero hits on `main`. SHAs cited in the issues' own receipt comments point plausibly to v0.2.8 for the V28 issues and v0.2.9 for the V29 issues. But a backticked SHA can be a baseline rather than the fix, so those are proposals to confirm, not answers. Newer vox work is in much better shape. **83 of 121 Release ready issues already have a `main` commit through the timeline**, because the `merge: #N` subject creates a `ReferencedEvent`, and all 83 correctly compute to "unreleased" pending v0.2.10 ([vox #182](https://github.com/robertelee78/vox/issues/182)). The other 36 reference only unmerged branches, and some of those commits no longer exist in any ref (8 of 11 for [#282](https://github.com/robertelee78/vox/issues/282)). r2c's ADR-059 epics (M0–M6) are long-lived and reopened, so "first release" is defined only per accepted delivery, not per issue.

## A portable convention makes direct pushes attributable

vox shows that requiring a closing PR is the wrong fix. It would force a workflow on a repository whose owner deliberately integrates locally, which conflicts with the rule that the skill must stay independent of any one repository's process ([AGENTS.md](../AGENTS.md)). A closing keyword in the merge commit fails for a different reason. GitHub closes the issue the moment the commit reaches the default branch, which is before the release a `next` or exact-tag story is waiting for, and it still does not link a PR ([linking PRs](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)). The convention should work the same for a PR merge, a local merge commit, and a direct push. It has three parts.

The first part is a **trailer on the integrating commit**. Whoever lands the change on the default branch, agent or person, puts `Work-item: #N` (repeatable) in the message of the commit that reaches the branch: the merge commit, the squash commit, or the single direct-push commit. Using `Refs`-style wording rather than `Closes` produces the timeline `ReferencedEvent` without closing the issue. Unlike a subject prefix, a trailer can be parsed with `git interpret-trailers` and survives rewording. vox's `merge: #182 — …` subjects already do most of this, so the change for vox is to formalize the existing habit, not replace it.

The second part, which carries the most weight, is **an `integration` evidence record written by the agent**. When a story enters Release ready, the agent records the commit URL of the default-branch SHA, plus the PR URL when one exists. Each record binds to the accepted `candidate`. When the candidate is a branch commit, awa checks that the integration SHA is a merge or squash that contains the candidate, by ancestry or through the PR's `merge_commit_sha`. That one record covers vox's direct pushes and r2c's docs-only closing PR. It also makes the attribution independent of how the issue was later closed.

The third part is that **a backport is a second integration record**, made on the release branch with `cherry-pick -x`. It is never inferred. Kubernetes uses the same model: cherry-pick PRs link back to their origin PR, and unlanded picks stay tracked for the next patch release ([Kubernetes cherry-picks](https://github.com/kubernetes/community/blob/main/contributors/devel/sig-release/cherry-picks.md)). Rust shows the alternative's weakness. Its milestone-at-merge approach is intent, not proof, and its own Forge admits items can be "missed indefinitely" ([Rust Forge](https://forge.rust-lang.org/release/issue-triaging.html)). For PR-based repositories, the `addCloseIssueReferences` link recommended earlier remains useful corroboration, and r2c already produces it. It is never a substitute for the integration record.

## Concrete changes to the skill pack

The changes fit the skill's existing evidence model rather than adding a side channel. Today `REQUIRED_EVIDENCE` gates Done on `delivery`. The only check on delivery is that `delivery.candidate` equals the accepted candidate, and the fixture uses an arbitrary `release:{attempt}` ref ([reconcile_project.py:63](../skills/github-work-accountability/scripts/reconcile_project.py); [scenario.py:148](../tests/scenario.py)). `bin/awa` currently offers only `update`, `version`, `doctor` and `status`, so the `release` verbs are new.

| Skill file | Change |
|---|---|
| `scripts/reconcile_project.py` | Add `integration` to `REQUIRED_EVIDENCE` for Release ready and Done on stories whose delivery is release or merge. Validate it: a 40-hex commit URL in the same repository and on the default branch, bound to `candidate`, with an optional PR URL and a `line` (`default` or a release branch) for backports. For release-kind Done, require `delivery.ref` to name a published, non-draft Release whose tag contains every integration SHA for that line. Store `tag_sha` and `immutable` in the delivery record, and refuse with the named `unknown` reason otherwise. Never infer a commit from a closer or a reference during reconcile |
| `bin/awa release close <tag>` | Verify the Release is published. For exact-tag members, verify containment. For `next` stories in Release ready, attribute each one: it lands on this tag only if this is its first containing published release. Print attributed, deferred (not contained) and `unknown` lists separately. Write delivery evidence and the release milestone for the attributed stories, and refuse to close the milestone while any member is `unknown`. Containment uses the local repository only when it is not shallow and its tags match `ls-remote`; otherwise it uses REST compare. A dry run shows the exact evidence it would write |
| `bin/awa release backfill [--since <tag>]` | Read-only proposal for stories that are already Done or closed. For each one, show the resolved change (from evidence, then closer, then merged closing PR), the first published release, and every candidate commit from references or receipt text, which are never used automatically. Writes happen only through `--accept <issue>=<tag>` or an accepted proposal file, so every ask-case answer is recorded as a decision rather than a guess |
| `bin/awa release attribute <issue>` | The same procedure for one story, for agents to run before claiming delivery |
| Managed block and `references/synchronization-contract.md` | Add a generated "Integration:" line (commit and PR links) next to "Delivery boundary", and a "Delivered in: vX (first published release containing <sha>)" line, or "Delivered in: unknown — <reason>". Both are generated from evidence, so people read them and nobody edits them |
| `SKILL.md` and `references/work-model.md` | Tell agents to write the `Work-item: #N` trailer, record integration evidence at Release ready, use `cherry-pick -x` with a second record for backports, avoid closing keywords on release-kind stories, and never cite release-note `#N` mentions or `describe --contains` as delivery. State the attribution rule and the `unknown` triggers in plain words |
| `references/github-model.md` | Record the API facts: `includeClosedPrs:true`, `ClosedEvent.closer` types, `merge_commit_sha` semantics by merge method, compare status vocabulary, `published_at` rather than `created_at`, drafts visible only with push access, immutable releases, and the shallow-clone false negative |
| `scripts/gh_account.py` | Reuse one verified identity for a whole run instead of making a `GET /user` call per request |

Following the repository's rule, the simulator should prove each increment through the real CLI and assert on what a release manager sees ([AGENTS.md](../AGENTS.md)). `tests/github_sim.py` needs:

- a commit graph per repository, with tags, both annotated and lightweight
- Releases with `draft`, `published_at`, `created_at` and `immutable`
- `GET /compare/{base}...{head}` returning the four statuses
- `closedByPullRequestsReferences` that hides merged PRs unless `includeClosedPrs` is passed
- `ClosedEvent.closer` and timeline `ReferencedEvent`s

The local-git path can use a temporary repository built inside the test, which stays deterministic and needs no credentials. The scenarios should read like the pilots:

- An r2c-shaped run where `awa release close v0.1.13` attributes #1351 and #1352 but first asks about the release-less v0.1.12.
- A vox-shaped run where a direct-push story with a `Work-item:` trailer and integration evidence attributes correctly, and an identical story without evidence lands in `unknown: no linked change`.
- A story whose earliest reference is in v0.2.9 but whose latest integration is untagged, which must defer.
- A shallow checkout that falls back to the API instead of answering "not released".
- A draft release that is refused.
- A `cherry-pick -x` backport published before the mainline release, which yields `unknown: backport`.
- A revert inside the range, which yields `unknown: reverted`.
- A docs-only closing PR that conflicts with the recorded candidate.
- A mutable tag moved after attribution, which triggers recomputation.

## Conclusion

The pilots move the problem from "which release contains this commit", which is solved and the same through git or the API, to "who wrote down the commit". That question belongs to the agent at integration time, not to the reconciler after the fact. r2c looks healthy only because its PR-only workflow makes GitHub record the link as a side effect. vox shows that the link disappears as soon as a team integrates any other way. Even r2c's clean cases broke twice when "what closed the issue" was not "what was delivered". So the durable fix is an `integration` evidence record bound to the accepted candidate, not a better heuristic. Making `unknown` a first-class, reasoned output is what lets the skill be strict without being useless: backfill becomes a short list of decisions for the owner, and new work stops adding to that list.

Three product decisions remain open:

1. Do prereleases count as "published"? They are non-draft, so the owner's rule includes them as written.
2. Should a tag without a Release always be asked about, or only the first time per tag? r2c's v0.1.12 affects four stories at once.
3. Should `integration` evidence be required for merge-kind stories, or only for stories whose delivery is a release?
