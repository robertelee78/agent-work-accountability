# ADR-001: Milestone administration without lifecycle transitions

**Decision status:** Proposed
**Date:** 2026-11-14
**Updated:** 2026-11-14
**Target release:** v0.10.16

## Context

AWA 0.10.15 treats a release milestone's title as both scheduling identity and release tag. Full-document manifest parsing calls `validate_story_evidence` and `validate_delivery_evidence` for every story before milestone planning. Drafts recover evidence primarily from manifests previously applied on the current machine. Therefore a scheduling-only edit can require reconstructing unrelated historical acceptance evidence. Epics are prohibited from carrying manifest milestones even though GitHub supports assigning them.

Read-only observation of IOMachines/cve-to-exploit on 2026-11-14:

- https://github.com/IOMachines/cve-to-exploit/milestone/19 is currently titled `v0.0.20`; it contains zero open issues and 37 closed issues.
- https://github.com/IOMachines/cve-to-exploit/milestone/20 is currently titled `v0.0.21`; its enumerated issues include 34 open and six closed issues, excluding pull requests.
- Issue #548 belongs to milestone 20 but records `Release: v0.0.20` and `Delivery: release v0.0.20`; #35 belongs to milestone 20 but records `v0.0.19` in both lines. Epic #214 also belongs to milestone 20.

These are observations, not a claim about who changed the milestones or whether any issue was delivered. The earlier report of nineteen remaining source issues is no longer current. GitHub milestone counters include pull requests and are not acceptance evidence.

The operator needs to move open issues and rename milestones, not change task status, reconstruct evidence, publish releases, or maintain two competing scheduling records. The portable skill and its executable must support the same operations on user-owned and organization-owned repositories.

## Decision

Scheduling and historical delivery are separate authorities. GitHub owns current milestone identity, title and membership. AWA owns the explicit association between a scheduling milestone and a future release target, when one is declared. Proven delivery keeps its immutable release/candidate/integration facts. A milestone title is not proof of a release binding or delivery.

This ADR specifies new behavior; commands below are not available in 0.10.15. The work is planned for v0.10.16, not implemented or accepted by this document. Its proposed status does not make implementation stories Ready.

### 1. Stable identity and legacy migration

- AWA MUST identify a milestone by GitHub host, repository identity and milestone number, retaining its node ID when available; titles are mutable display values. Numeric CLI selectors are repository milestone numbers, not REST database IDs.
- GitHub membership MUST be the sole per-issue scheduling authority. For an undelivered release story, the intended tag MUST derive from its live milestone's explicit release binding, not a copied issue-body title. AWA MUST NOT introduce another per-issue target record or a routine sync command.
- A release binding MUST live in the milestone description as `<!-- work-accountability:release-tag TAG -->`, preserving all surrounding human text. Each milestone MUST bind at most one tag and each tag at most one milestone in the repository. Missing, duplicate, malformed or conflicting markers MUST be reported, not guessed. `awa release plan TAG` MUST create-and-bind only after checking all milestones; `awa release plan TAG --milestone NUMBER --reason TEXT` MUST bind an existing milestone. Description updates MUST preserve the marker. Correcting a different existing binding MUST require `--rebind --reason TEXT` and MUST be refused if the old tag has any published Release, a member is Release ready or Done with integration/delivery evidence for the old tag, or an unfinished release-close ledger references it. Unavailable proof for these safety checks MUST cause refusal, not assumption.
- Migration MUST be read-only unless the operator explicitly binds a milestone or an ordinary permitted write lazily cleans legacy scheduling lines from an open, non-Done issue. `Release:` and undelivered `Delivery: release TAG` MUST become legacy hints, not scheduling authority; the latter MUST normalize to delivery kind `release`. `release next`, `merge` and `other` MUST retain their distinct semantics. A candidate legacy binding MAY be suggested only when the title equals the tag, no other binding claims it, and every managed member's legacy hints agree. Existing unbound milestones MUST never be silently adopted or replaced by create-by-title behavior; a same-title unbound milestone MUST produce an explicit bind instruction.
- Create-and-bind MUST also refuse if a different milestone has managed members with legacy hints naming the requested tag, displaying those identities for explicit resolution. `Planned delivery: release TAG` from extraction MUST seed only an unassigned issue; a disagreement with live membership MUST be a note, never an implicit move on redraft.
- For Done stories, historical tag authority MUST be `evidence.delivery.release` corroborated by `Delivered:` and the actual Release; validation/check_delivery MUST never compare that tag to current scheduling membership or title. Drafts MUST preserve historical proof and MUST NOT derive it from a live milestone. Administrative migration, move and rename MUST NOT rewrite closed or Done issue bodies. Release ready stories, although often closed by AWA, remain undelivered and MUST still use the explicit release binding when validating release completion.
- A new project manifest schema MUST record observed milestone numbers separately from delivery evidence and express explicit desired scheduling changes by identity. Old project-v4 manifests MUST be rejected as apply inputs with redraft instructions, but MUST remain readable as remembered/--base evidence sources with scheduling fields ignored. Existing release-close ledgers tied to old apply manifests MUST stop before further writes and explain how to archive the ledger and re-inventory into a new operation; verified prior progress MUST remain idempotently recognized.
- The normal reconciler, extraction/draft generation, ensure_milestone, release status/close/backfill, document status summaries and release-next resolution MUST cut over to the same identity/binding contract. No consumer MAY create a duplicate milestone after rename or rederive a delivered tag from its title. Unmanaged and epic members MUST be reported separately as non-delivery members, not rejected merely for membership or counted as delivered. Open such members MUST prevent automatic release-milestone closure unless explicitly moved; release close's existing move-open option MUST use the same open-only move primitive. No release operation MAY fabricate acceptance for these members.
- Release close MUST apply its evidence-validated document transitions first, then re-enumerate milestone membership, then check or move only members still open, and close the milestone only after those effects verify. Its close ledger MUST embed/reference the shared move's portable operation receipt and resume these stages without repeating completed lifecycle effects. It MUST NOT move or refuse an epic that these same document transitions just completed.

### 2. Narrow move and rename operations

- AWA MUST provide `awa milestone move --repo OWNER/REPO --from NUMBER --to NUMBER --open-only --reason TEXT [--dry-run]` and `awa milestone rename NUMBER --repo OWNER/REPO --title TEXT --reason TEXT [--dry-run]`. Both default to execution when `--dry-run` is absent. The move in this release MUST require `--open-only`; moving closed issues is outside scope.
- Move MUST enumerate all pages of source membership, select only open issues, exclude pull requests, and include both stories and epic containers. It MUST NOT recursively move descendants absent from that selection. It MUST require distinct existing source/destination milestones and an open destination; it MUST NOT create, rename, close or reopen a milestone.
- Move MUST change only selected issue milestone assignment and post its reason/intention comment. It MUST NOT rewrite issue bodies. It MUST preserve issue state/state reason, Work phase, Health, source freshness, priority/rank, labels, assignees, hierarchy, attempts, acceptance/integration/delivery evidence, and human-authored text. Epic membership MUST NOT introduce epic lifecycle or delivery claims. Unmanaged issues MUST move under the same open-only selection without acquiring managed blocks.
- If any selected managed undelivered release story requires a destination release binding, the destination MUST have a verified explicit binding before any mutation in the operation. An unbound destination MUST refuse the entire operation with the bind command to run. Other delivery kinds MUST remain unchanged. The live membership change then changes the intended release target by derivation, with no copied tag update.
- Rename MUST be one title PATCH plus read-back: preserve identity, description/binding, due date, state and membership, accept ordinary non-tag titles, and perform no issue or Project writes. It MUST NOT rename tags/releases. A title equal to another milestone's bound tag MUST be refused; a tag-shaped title different from its own binding MUST produce a warning naming the unchanged binding. AWA summaries MUST refresh from live titles/bindings at the next ordinary reconciliation; custom saved views and human prose MUST never be rewritten.
- Rename MUST refuse an unbound milestone with a tag-shaped existing title or any managed undelivered release-kind member, including closed Release ready stories, and explain `awa release plan TAG --milestone NUMBER --reason TEXT` before retrying. Binding before rename MUST preserve the intended tag; unknown legacy intent MUST require an operator choice rather than a guessed binding.

### 3. External edits and read-only diagnosis

- AWA MUST provide read-only `awa milestone status --repo OWNER/REPO [NUMBER]`, displaying live identity/title, explicit binding or suggested legacy candidate, and member-level legacy disagreements with both values. It MUST work for unbound milestones without a tag argument and MUST separate missing lifecycle evidence from scheduling diagnostics.
- Same-identity title edits MUST require no repair. GitHub-side membership edits MUST become the live schedule without a sync ceremony; inherited child milestones follow the same rule. Ordinary reconciliation MUST note changes and preserve live assignments unless the request explicitly changes scheduling. A draft's unchanged scheduling field MUST keep live membership; an explicit scheduling mutation MUST conflict if its observed milestone number changed before apply. Unbound or conflicting bindings MUST block only an operation that actually needs a resolved release target, not unrelated administration or read-only diagnosis.
- Legacy cleanup MUST occur lazily only on an otherwise authorized open, non-Done issue-body write, preserving unrelated bytes. An evidence-validated lifecycle transition into Done MUST remove obsolete scheduling hints in that same write; already-Done bodies MUST remain untouched. Every cleanup receipt MUST retain removed legacy values and their replacement semantics. Cleanup MUST NOT be required before move/rename or cause full-document evidence reconstruction. There MUST be no bulk evidence migration or implicit binding inferred from stale body lines.
- Administrative requests MUST have a closed field whitelist; lifecycle/evidence/attempt/delivery-proof inputs MUST be rejected, not ignored. Their validation path MUST NOT construct a full document lifecycle manifest. Normal reconciliation and all lifecycle/evidence mutations MUST retain the existing evidence requirements; this decision does not introduce delta-based relaxation of those gates.

### 4. Concurrency, retries and truthful receipts

- Each administrative run MUST verify the selected actor and repository permissions, inventory before writing, and enforce existing locks/pacing/write-budget controls. Milestone administration MUST NOT require Projects capability or vary semantics by owner type. Dry runs MUST perform no content mutations and list exact selected issues, skipped issues, bound release targets and estimated writes, including a separate warning for closed-but-undelivered members (for example Release ready) that open-only deliberately leaves behind.
- Before a move's first mutation, AWA MUST persist a portable versioned operation receipt containing a fresh operation ID, exact selected issue numbers, observed source/destination identities, observed titles, actor, reason and progress. The ordinary command MUST resume a matching unfinished local operation without widening selection; incompatible pending operations MUST stop with resume/abandon instructions. `awa milestone move --resume FILE` MUST allow another machine to resume that same selection from the portable receipt without historical lifecycle manifests. Without that receipt a new run MUST explicitly be a new inventory, not claim recovery of unrecorded progress. Repeated source/destination/reason combinations after a completed operation MUST get fresh IDs.
- Per selected issue, the write order MUST be: re-read eligibility and assignment, post/read-back a deduplicated intention comment containing operation ID/issue/source/destination/actor/reason, re-read eligibility and assignment, PATCH only the milestone, then verify. Intent comments MUST not claim success; receipts carry verified outcomes. Lost responses MUST be resolved by reading the marker and assignment before retrying. Destination members MUST count as already-applied only if selected in the receipt and carrying this operation's marker; unrelated destination members MUST never be claimed.
- Intent deduplication MUST key only on operation ID and issue number, not actor; a resumed actor MUST be reported separately. When assignment is back at source but the receipt lacks a verified outcome, resume MUST inspect milestone timeline events after the intention to distinguish never-applied writes from a later manual revert. A revert or inaccessible/ambiguous timeline MUST conflict rather than silently reapply.
- An issue closed since selection MUST receive no further writes and be reported as skipped, distinguishing a pre-existing intent from a new effect. A third-party assignment MUST be a conflict. The tool MUST preserve all bodies byte-for-byte because move never PATCHes them. GitHub issue PATCH has no atomic compare-and-swap; the tool MUST document the remaining close/assignment race between final read and PATCH and MUST NOT promise atomicity or absolute closed-issue exclusion during that window.
- Rename MUST not use a multi-step journal: persist/report observed and desired titles in its portable receipt, and accept that receipt via `--resume FILE` after an uncertain response. Desired title means already-applied; observed title permits retry; any third title is a conflict. An ordinary fresh rename is a new explicit request, not an inferred retry. No follow-up issue/Project refresh writes are part of rename.
- Receipts MUST enumerate selected, moved, already-applied, skipped-closed, conflicted, failed and pending items, with reason/assignment verification per issue and intent-only effects disclosed. `verified: true` MUST mean all required effects or verified skips in the selected operation were read back, with no unresolved conflicts/failures/pending effects; it MUST NOT certify lifecycle acceptance or immutable-state preservation against independent concurrent writers. No-op runs MUST not claim moves. Silent permission drops MUST fail verification. Retryable budget/rate/network stops MUST retain progress and exit 75; conflicts MUST exit 2. Rename MUST verify its preserved milestone attributes and disclose the same non-atomic race.

### 5. User-visible regression and case-study proof

- Regression coverage MUST drive the real CLI against `tests/github_sim.py` with isolated state and no credentials/live writes. Fixtures MUST represent stale legacy titles, explicit/unbound release bindings, epic and unmanaged membership, missing historical manifests, and mixed open/closed issues and pull requests. C2E-specific values are fixtures, not product special cases.
- Proof MUST show open-only selection across pagination, preservation of non-whitelisted fields and byte-identical bodies, arbitrary-title rename with stable identity, unchanged release bindings and historical proof, external assignment without a sync ceremony, explicit binding of a stale legacy case, and safe refusal of ambiguous migration or lifecycle-bearing administrative input. Renaming a milestone containing Done issues followed by an evidence-complete ordinary reconcile MUST produce zero writes to those closed historical issues. Ordinary lifecycle/evidence changes with missing/invalid proof MUST still fail existing validation.
- Fault scenarios MUST cover closure/assignment races, independent body edits surviving moves, an independently changed rename title, silent permission drops, write-budget exhaustion, old evidence-base reuse, old release-close ledger refusal, repeated move cycles, same-machine resume and portable-receipt cross-machine resume, and interruption/lost response at each mutation boundary. Retry receipts MUST distinguish prior verified progress from new writes, deduplicate reasons and leave unrelated destination issues untouched. Full-suite validation MUST pass with `./tests/run.sh` before publication.
- Regression proof MUST also cover binding-before-rename refusal, guarded correction of an erroneous binding, post-transition release-close membership and embedded move recovery, legacy cleanup receipts and Done-transition cleanup, extraction hints not overriding live membership, actor-independent intent deduplication, and lost-response/manual-revert ambiguity.
- Development MUST NOT mutate IOMachines/cve-to-exploit. A later separately authorized operational run MUST refresh the case-study inventory, preview the exact changes and use verified receipts, not the stale nineteen-issue report.

### 6. Portable guidance and release handoff

- The v0.10.16 implementation MUST update CLI help, README, entry routing, model, extraction, release planning/closing/backfill and board reconciliation guidance to distinguish scheduling from evidence-bearing delivery. It MUST replace the UI-edit prohibition with GitHub-membership authority and observed-number conflict rules, and remove the same-machine-evidence requirement for administration only. Existing lifecycle evidence gates MUST remain documented and enforced.
- Documentation MUST include move, rename, status and explicit binding examples; dry-run/execution behavior; number semantics; closed-but-undelivered exclusions; migration/evidence-base compatibility; portable-receipt resume and fresh-run semantics; reason intents; truthful receipt meanings; and remaining non-atomic races. Administrative commands MUST follow release plan/close's direct execution precedent, explicitly contrasting reconcile's --apply convention. Documentation MUST explain that titles/counts prove neither release identity nor delivery.
- Implementation order MUST be identity/bindings/migration first; move/rename and external-edit diagnosis depend on that contract. Recovery/verification completes those operations before regression acceptance and documentation/handoff are complete. All implementation stories MUST target v0.10.16 without treating milestone assignment as approval, acceptance or delivery.

## Alternatives and consequences

Weakening full-document evidence validation would expand trust beyond this scheduling problem and is rejected. Another canonical per-issue scheduling record, routine move-then-sync ceremony, automatic release-tag renaming, and bulk historical-body migration are rejected. Live membership plus one durable milestone-to-tag binding remove the stale-record problem rather than perpetuating it. Full event-store/evidence-portability redesign is outside this release; binding corrections remain narrowly guarded against changing accepted or published delivery intent.

Stable identity requires a schema and consumer cutover, including historical validators, not another title alias. Binding decisions are explicit only where scheduling previously concealed ambiguity. Rename remains a single milestone write; move needs an auditable intention and a recoverable assignment. A portable operation receipt preserves exact selection across machines without inventing lifecycle evidence or pretending GitHub supports multi-object transactions.

## Review and approval

The operator requested deeper design, independent Opus review, a source-bound GitHub Project and implementation tasks assigned to v0.10.16. Independent review findings must be resolved before decomposition. Opus review is design feedback, not operator approval or implementation acceptance. This ADR remains Proposed until its decision authority accepts it.

Opus review identified undefined binding storage, duplicated per-issue scheduling authority, historical validators tied to titles, legacy evidence compatibility, incomplete cross-machine recovery, and unmanaged/epic release-close handling. This revision defines durable description markers, removes sync and per-issue target copies, makes historical delivery independent, retains v4 evidence reads, uses portable selected-operation receipts, and specifies non-delivery member handling. Deterministic IDs derived only from reason/source/destination were not adopted because repeated move cycles could collide; fresh operation IDs plus explicit receipt resume preserve identity without widening selection.

The second Opus pass found three remaining high issues: unbound rename could lose release intent, mistaken bindings lacked a correction path, and release-close membership checks needed stage ordering. The final amendments require bind-before-rename and legacy collision checks, guarded explicit rebinding, and post-document-transition member checks with the shared move receipt in the close ledger. Its five medium findings are also included: timeline-based revert ambiguity, Done-transition cleanup, cleanup receipts, non-authoritative extraction hints and actor-independent reason deduplication. Opus stated the ADR is ready for task decomposition once these amendments are included; this is not implementation acceptance.
